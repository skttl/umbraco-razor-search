# Release validation

Status on 2026-09-09: implementation, build/package validation and the SQL Server runtime checks below are complete. Final packages on both Umbraco majors passed the two-process load-balancing matrix. Visual backoffice acceptance and Marketplace screenshots remain outstanding. SQLite verification is deferred for the first beta by the user's decision.

## Completed build and package checks

- Client installation, TypeScript checking and Vite builds passed. The completed client dependency audit reported no vulnerabilities.

- The final Release suites each passed 83 tests on Umbraco 17 and 18 with zero failures or skips, including actual Examine-provider behavior and SQLite/SQL Server persistence. Both final candidates were packed, their package contents checked, and their demo apps published after this run. The queue regression includes retaining the recorded attempt count when a persistence exception reaches the outer worker handler.

The reusable installed-package acceptance app now reports `ready` and `bootFailed` from its health endpoint and rejects mutation requests with HTTP 503 until `IContentRoutingReadiness.IsReady`. This avoids seeding before unattended-upgrade startup handlers finish. The changed acceptance fixture compiled against fresh isolated candidate caches on both majors; both Release solutions also built successfully. These test-driver changes do not change the package DLLs or the previous 83-test regression results.

## Follow-up runtime checks after explicit approval

On 2026-09-09, the existing Umbraco 18 SQL Server publisher completed a full background rebuild over 5,007 published documents. The request was accepted at 10:24:32 UTC, discovery reached `queuedAll` at 10:25:30, and the render worker was idle at 10:25:33. Discovery reported 5,007 documents, 5,008 queued routes, zero skipped documents and no discovery error.

The route count comprises 5,005 invariant documents and two variant documents: one with English/Danish and one with English only. During rebuild, partial unpublish removed the first document's Danish snapshot. All 5,007 remaining snapshot rows were successful and had an update timestamp after rebuild acceptance. Both English snapshots remained. This verifies the full SQL rebuild exceeds the former 5,000-document boundary and that an in-flight rebuild did not recreate the removed culture's snapshot. The publisher query also stopped finding the Danish token. The subscriber converged to zero Danish matches at 10:28:16 UTC, about three minutes after unpublish at 10:25:15 under the 5,008-route rebuild. During that interval, the subscriber returned no Danish items but temporarily reported a stale total of one. Its local Lucene index continued changing throughout. Both nodes retained two English results. This verifies partial-culture removal reaches the separate frontend index under rebuild load; the observed delay is not a guaranteed refresh interval.

This run used installed `18.0.0-beta.acceptance.4`, not the final normal beta package. The later source corrections cover invariant result URLs and attempt-count metadata. Final-candidate runtime checks remain explicit below.
An earlier new Umbraco 18 frontend index has explicit bootstrap evidence: its log started rebuilding `Umb_RazorSearch` at 09:41:24 UTC and indexed invariant, English and Danish documents at 09:41:25. This used an earlier acceptance candidate; the current running frontend reuses that index. The prepared final installed fixture references both normal `18.0.0-beta.1` packages, and its core DLL SHA256 matches the current Release build exactly. This confirms the fixture contains the current binary, but does not substitute for starting and exercising it.
A bounded, networkless SQLite diagnostic reproduced the CMS table-order conflict using two connections and WAL on a fresh database. The writer updated `umbracoDocumentVersion` before `umbracoNode`; the reader read Node before its joined Version count. With shared cache both operations failed after about 1.1 seconds with `SQLITE_LOCKED_SHAREDCACHE` (6/262), naming the respective conflicting tables. With private cache the same operations succeeded immediately and the reader observed its earlier snapshot. This establishes the database mechanism matching the original traces. The original HTTP unpublish ultimately returned 500 after 602 seconds of retries. It does not by itself establish a production fix; the full CMS differential test remains separate.
The full CMS comparison subsequently used fresh, separate SQLite databases and content roots, CMS 17.6.2 and the final `17.0.0-beta.1` candidate. Its core DLL SHA256 matched the version-line Release build. Both hosts used networkless TestServer transport and waited for `IContentRoutingReadiness.IsReady` before seeding, because unattended upgrade can report runtime `Run` before startup notifications and package migrations complete. Both produced the initial culture snapshots. The shared-cache case stalled during its first concurrent rebuild/unpublish, with stacks in CMS `Unpublish` and `GetPagedDescendants`. The private-cache case completed two cycles, then stalled in CMS `ContentRelationsUpdate.PersistRelations`. Both exited with the diagnostic's explicit 180-second failure deadline. The diagnostic uses a five-second default SQLite command timeout; this is not the original production timeout/retry duration.

A dump from an earlier initialized private-cache run established SQLite error 5, extended code 517 (`SQLITE_BUSY_SNAPSHOT`) in `RelationRepository.DeleteByParent`. The only live SQLite transaction belonged to that CMS relation-update scope; no other live writer remained. This is a stale read snapshot being promoted to a write transaction, distinct from the shared-cache table-lock cycle. Changing the cache setting alone therefore has not passed the full CMS acceptance case. No global connection-string rewrite, broad lock or replacement CMS notification handler has been applied. The reusable [networkless diagnostic](../../tests/diagnostics/sqlite/README.md) records the scenario without opening ports or touching an existing site; it remains a failing diagnostic, not part of the passing regression suite.

Two additional bounded stock-CMS 17.6.2 runs, with no RazorSearch dependency, also timed out on their first concurrent descendant-read/partial-unpublish operation using shared cache, at 20 and 60 seconds respectively. Managed stacks from the second run showed CMS `Unpublish`/`PersistUpdatedItem` and `GetPagedDescendants` stalled. This independently reproduces the shared-cache issue without RazorSearch; the private-cache relation-update failure above was observed with RazorSearch installed and is not claimed as a stock-CMS reproduction.

## SQLite deferred for the first beta

Decision on 2026-09-09: the user asked to skip SQLite verification for the first beta. SQLite remains available, but concurrency and large-dataset SQLite tests are no longer beta release gates. The observed failures remain documented and have not been declared fixed. Further SQLite investigations were stopped; already-running bounded diagnostics were allowed to finish their own deadlines.
An observed 17 SQLite run started a rebuild and immediately unpublished one culture. The unpublish request stalled and a worker save reported SQLite error 6, `database table is locked`. A later read of the original operation established that discovery failed at 09:56:43 UTC after starting at approximately 09:46:41, reporting `database table is locked: umbracoDocumentVersion`. This was a prolonged stall followed by failure, not a proven permanent deadlock; CMS command timeout/retry behavior prolonged the wait. This remains an observed defect, but the user has explicitly deferred SQLite verification for the first beta. Managed stacks and a local diagnostic dump show blocked CMS NPoco transactions before lifecycle notifications; both package EF scopes were disposed and unrooted. No package lock-order fix has been applied because that diagnosis was not supported. The fixture uses `Cache=Shared`, which is also the connection-string setting generated by [Umbraco 17.6.2 itself](https://github.com/umbraco/Umbraco-CMS/blob/release-17.6.2/src/Umbraco.Cms.Persistence.Sqlite/Services/SqliteDatabaseProviderMetadata.cs). Removing it is a diagnostic comparison, not proof that the original failure was caused by an unsupported fixture setting. A future SQLite verification must prove completion, preservation of the still-published culture, removal of the unpublished culture, and no resurrection by an older render job. Native lock ownership has not been established.

## Final Umbraco 18 SQL Server restart and frontend checks

A bounded diagnostic using the installed `18.0.0-beta.1` packages passed the following checks against its own SQL Server database. Each stage ran in a separate operating-system process. ASP.NET Core TestServer handled HTTP requests in memory; no TCP listener or existing application was started or stopped.

- The publisher returned the expected invariant/English/Danish totals of 1/2/2, including valid public URLs for invariant results in culture-specific searches. It then terminated its own process with one running render job and three queued jobs.
- A new publisher process started with an empty queue. All three successful snapshots retained their IDs, text and timestamps. A manual rebuild updated those same snapshots and completed without failed jobs.
- A separate subscriber started with no index directory. Its new Examine index returned the same 1/2/2 culture results and valid URLs within seven seconds. Its render queue remained empty.

The reusable [restart diagnostic](../../tests/diagnostics/RuntimeRestart/README.md) builds independently on both version lines. These results establish queue loss, snapshot persistence, manual recovery and fresh-frontend indexing with the final package. They do not verify TCP/proxy routing or browser behavior.

A subsequent clean first-boot run also passed publication, three successful snapshots and the 1/2/2 search results with valid URLs in one process, without restarting. The final run exited zero and checked Total, Items and all URLs in the same HTTP response for each culture. Readiness was recorded at 11:11:18 UTC and the successful samples at 11:12:22, about 64 seconds later. Earlier diagnostic copies had omitted the readiness check before accessing content services, despite the general acceptance fixture already having it. One attempted publication therefore reached Search before its database table existed. The corrected diagnostic waits for `IContentRoutingReadiness.IsReady` before any content-service calls and rejects early mutations with HTTP 503. Initial search responses were still empty while the index became visible, then converged within the bounded query deadline. The early missing-table failure does not establish a Search or RazorSearch startup defect.
